AIOrc makes your AI agents follow the workflow you define, instead of skipping steps and going off-script.

“One developer builds a flow... everyone uses it.”

Your AI agents skip steps and ignore the process you defined. AIOrc fixes that at the root: in the default server-orchestrated mode, a server drives execution one step at a time and rejects anything your workflow doesn't allow, so agents can't skip a step or take a transition the graph does not allow. Design the process once, share it with your team or the community, and, when you need it, audit every run as signed evidence.

Design it once. Run it verified. Prove what happened.

Building agents is the easy part. The hard part is knowing they followed the right process. AIOrc turns a visual workflow into a contract the server enforces, and a record you can audit. No new tool for your team: it works through the AI clients they already use.

  1. 01

    Design the flow

    Connect agents in the visual Flow Builder. Branch with natural-language conditions on the edges, fork with Parallel nodes, iterate with back-edges.

  2. 02

    Connect once

    Each teammate connects their AI client (Claude Code, Cursor…) with their own personal token and one committed .mcp.json entry. No new app to learn: the workflow shows up where they already work.

  3. 03

    Run it verified

    In server-orchestrated mode (the default) the server drives execution one step at a time and rejects any move the flow doesn't allow. Agents cannot skip a step or take a transition the graph does not allow.

  4. 04

    Audit & govern

    Every server-orchestrated run is recorded step by step, and every run is exportable as signed, tamper-evident evidence. Pause any project instantly, see which agents actually run, and prove the process was followed.

Everything you need to put agents in production, and keep them in line

Govern, verify and audit your team's agents, and reuse what works across every project.

Enforce

The graph is a contract, not a suggestion.

Two execution modes, one switch per project

Server-orchestrated (default): the server hands out one step at a time, validates every output, decides rule-based transitions and checks every other one, and records every dispatch as ground truth. Model-orchestrated: the whole flow in a single response, no round trip per step, finished with a report the model writes itself; labelled self-declared everywhere and never counted as verified. Pause any project's new runs, or cancel a single run, without touching the rest.

Conditional routing

Natural-language conditions on edges, priorities, parallel forks and loops via back-edges with per-node caps. Decisions and gates are patterns, not extra plumbing.

Fail-closed by design

Structural validation on save and again before every run: single Start, valid agent references, well-formed forks, every node reachable and able to reach an End. Cycles are legal loops with per-node caps, which the server enforces in server-orchestrated mode.

Deterministic evals

Test cases per flow, graded by the server against the verified execution path. Know whether a change to an agent improved the flow or broke it, before your team finds out.

Govern

Know who ran what, and prove it.

Signed audit trails

Every run is reconstructable step by step: who ran it, which transitions it took and why. Export any run as Ed25519-signed JSON with a hash-chained event log: tamper-evident evidence, aligned with EU AI Act logging requirements.

Live usage analytics

Which agents, skills and contexts actually run, per project and per teammate, minute by minute. Graph-aware skip detection separates real failures from branches not taken.

Multi-project with auth

Project keys and personal tokens, user and admin roles, per-project invitations, run history and an admin panel. Not a paid tier.

Reuse

Build on what already works.

Agents in markdown

Define each agent as a .md file. Its content is frozen when a run starts and handed to the model as that step's instructions.

Reusable skills

Package specific capabilities as skills and share them across projects and teams. Build on what already works.

Contexts: domain apart from capability

Business knowledge lives in Contexts, not inside agents. The same generic crew serves every project: inject the domain, reuse the capability.

One connection per project

Each project is one MCP connection. Workflow tools and the external MCP servers you register are exposed through it: proxied, namespaced and logged, and callable only during a server-orchestrated run by an agent allowed to use them.

The engine, under the hood

In server-orchestrated mode the engine keeps the state machine on the server. It freezes the agents a run uses, dispatches one step at a time, validates every output against the agent's schema, decides rule-based transitions and checks every other one against the graph, and writes every event to a hash chain that exports as Ed25519-signed evidence.

Origin

As a Software Engineer and AI researcher at my company, I was assigned to evaluate the state of the art in LLMs and agentic models. My recommendation was to adopt Claude Code. That's where the real problem started.

Two paths to orchestrate agents

I first tried to orchestrate agents deterministically using only the models. It didn't work: LLMs are probabilistic and often choose the path of least resistance instead of the correct one. The model ended up creating its own agents and skipping the ones I had defined.

Then I built a plugin for Claude with a main orchestrator, 21 subagents and 17 skills, using agent teams. It worked better, but the feature is still experimental and the bugs made it too unreliable for team use.

That's when I asked myself: what would a layer that runs deterministic prompt flows with agent orchestration, geared toward developers and dev teams, look like today? That's how AIOrc was born.

The problem it solves

At my company we have multiple projects with different stacks: a Nest.js backend with TDD, blockchain integration, fund custodians, AWS, MongoDB Atlas. A frontend with design patterns polished over years. If I wanted to use the flows my coworker had built, I had to ask them for agents, skills, context, copy them into my repo and hope Claude would follow the flow.

With AIOrc, my Claude connects to an MCP with a token. No cloning, no copying, no drift. When I migrate to Python tomorrow to add data science, I go to the public flow repository, grab what I need and use it.

A cross-disciplinary layer

We want AI to be universal. If we give Claude to a graphic designer, or if we give a backend developer who doesn't know styles the frontend flows from the team, the logic is exchanged. A developer shares the flow and the entire company, or the community, can follow their standards.

Where it stands today

Everything is oriented toward agents and automation with a clear goal: reduce execution time, gain reliability in the LLM and eliminate slop, that scattered, unreliable output models generate when they don't have a deterministic flow to follow.

It's just getting started. Today you can already create projects, orchestrate flows step by step under the server, or in model-orchestrated mode when speed matters more, define eval suites that grade runs against the graph, watch live usage analytics per agent, skill and teammate, share everything with your team privately, make public what you want and consume others'. The idea is to build a community of experts in web2, web3, blockchain, Python, C# and everything else we can think of, sharing secure databases, cloud connections, interface design and software architecture.

AIOrc is still a prototype in its early steps. What it needs now are people who try it, break it and share what happened. Early feedback is what defines where it goes, and the community is what will turn it into something truly useful. If what I'm building resonates with you, join in.
