How to use AIOrc

Multi-agent workflow compiler over MCP — getting started guide.

  1. 1
    Define the agents — In the Agents tab, create one for each logical step. Each agent is a Markdown prompt that the target model will execute verbatim as a section of the compiled flow.
  2. 2
    Define skills (optional) — Skills are auxiliary documents (TDD, standards, security patterns) that appear in the flow builder panel and that agents can reference by name.
  3. 3
    Create a project — In Projects. An MCP key is generated (format key-XXXX...) that you'll use in the target configuration.
  4. 4
    Build the flow — Open the project → Flow Builder. Drag agents from the left panel and connect them. Branch with natural-language conditions on the edges; fork with Parallel; iterate with back-edges (see the Control blocks tab).
  5. 5
    Save — The flow is validated and persisted. If there are structural errors (missing Start, broken agent references, malformed Parallel forks), they show inline and saving is blocked. Cycles are legal — a back-edge is a loop.
  6. 6
    Configure the target project — Add .mcp.json + a rule in CLAUDE.md (see next tab).
  7. 7
    Done — When Claude receives a task in the target, it will call workflow(request), AIOrc compiles the flow and returns a mega-prompt with step-by-step imperative instructions.

1. .mcp.json file in the root of the target project

Tells Claude (Claude Code, Cursor, or any MCP client) how to connect to the AIOrc server.

{ "mcpServers": { "aiorc": { "type": "stdio", "command": "node", "args": ["/absolute/path/to/AIOrc/mcp-bridge.js"], "env": { "AIORC_PROJECT_KEY": "key-XXXXXXXXXXXXXXXXXXXX", "AIORC_URL": "__AIORC_ORIGIN__/mcp" } } } }

2. Rule in the target project's CLAUDE.md

Tells the model to always call the workflow tool before responding. Without this rule, Claude may ignore AIOrc.

## Mandatory rule For any technical task (planning, implementation, code review, security, quality, bugs), always start by calling AIOrc's `workflow.start` tool (or `workflow` if start is unavailable). Never respond with a direct technical solution. In stepped mode, execute ONLY the agent the server hands you and advance with `workflow.next` — never skip or modify steps. ``` workflow.start({ request: "", context: "" }) ```
Replace /absolute/path/to/AIOrc/mcp-bridge.js with the real path (e.g.: /Users/me/dev/AIOrc/mcp-bridge.js) and key-XX... with the project's MCP key in AIOrc.

Decision, Gate and Loop are not separate node types — they are patterns built from plain agent nodes plus edges with conditions, priorities and back-edges. The only structural nodes besides Start/End are Parallel forks, whose branches ALL execute.

◇ Decision — content-based branching

Pattern: an agent followed by several outgoing edges with natural-language conditions. Edges are evaluated by ascending priority and a single transition is taken; an edge without condition acts as the fallback.

Example: "intent == 'bug'", "the agent determines it needs more context", "there are modified files in /src/security".

When to use: branch between agents (bug-resolver vs. new-fix), skip optional steps, choose a tool based on task type.

⛔ Gate — mandatory verdict

Pattern: the agent emits a literal verdict (PASS / FAIL / score ≥ X) and its outgoing edges carry conditions matching that verdict. Same structure as a branch — the verdict text is the condition.

Gate conditions are defined on the outgoing edges (literal verdict text).

When to use: after code-reviewer, security-qa, quality-gate, or any agent that returns a structured verdict.

↻ Loop — iteration with cap

Pattern: an edge pointing back to a previous agent (back-edge). Cycles are legal by construction; each agent carries max_invocations (default 10, max 50) which caps the repetition.

In compiled mode the target model keeps the count; in verified mode the server counts and enforces the cap itself.

When to use: review→fix→review until it passes, iterative refactor, retry tests with backoff, generate variants until a valid one is found.

The patterns combine freely (loops inside branches, gates after forks). In compiled mode the target model honors conditions and caps from the instructions; in verified mode (workflow.start / workflow.next) the server validates every transition against the graph and enforces the caps itself.

Welcome to AIOrc

A note from the person who built it

Hi — I'm Diego. I built AIOrc to solve two problems I got tired of suffering while working with AI agents — and chances are you know them too.

The first: sharing flows meant copy and pray. If you wanted to use the flow a teammate built, you had to ask for the files, copy them by hand into your repo and hope your Claude followed them the same way. Here that disappears: agents, skills and flows live in one place, your AI connects with a token, and if someone improves a crew, everyone gets the improvement instantly.

The second: agents don't follow the flows. They skip steps, invent their own agents, take the easy path. In verified mode, the server hands your AI one step at a time and rejects any deviation — skipping an agent becomes impossible.

And the third, which nobody had: the registry. Every agent on the team is registered and under control here — what exists, who owns it, which flows it's in and what it did, with every run audited step by step. With that come the data: live analytics of which agents actually run, who uses them, and tests the server grades on its own.

Where to start
  1. Browse the public repository and fork a crew that fits your work — one click, not an afternoon copying files.
  2. Or build your own: agents + flow in a new project.
  3. Open the project and follow the "Get this project running" steps to connect your Claude.
  4. And when you build something that works — an agent, a skill, a whole crew — make it public: someone else forks it, improves it, and the library grows for everyone.

This is an evolving prototype: what helps me most is that you use it, break it and tell me about it. Any blocker or idea, file it in Issues — early feedback is what decides where this goes.

Thanks for trying it.
— Diego
