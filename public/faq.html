AIOrc: a server-driven control plane for agent workflows over MCP

AIOrc stores a team's agents, skills and contexts, and exposes each project's workflow graph to any MCP client. The server never calls a model. By default it hands the client one step at a time, refuses to advance until each step's output matches the agent's JSON Schema, decides rule-based transitions itself and checks every other one against the graph, and writes each event to an append-only hash chain that exports as Ed25519-signed evidence.

Summary and positioning

Agent frameworks and workflow tools usually hand the model a plan and trust it to follow along; what actually happened is then reconstructed from the model's own account. AIOrc takes the opposite position: the workflow graph lives on the server, the server releases one step at a time, and a step only counts once the model hands back an output of the declared shape.

The model still does the work: it reads the instructions, runs tools in its own environment and produces the outputs. AIOrc is the contract and the auditor. That split is deliberate: the server stays small, deterministic and free of any model dependency, and every claim it makes about a server-orchestrated run is something it checked itself; model-orchestrated runs are stored and labelled as self-declared.

Key idea

The server cannot know whether a review was good. It can know, and prove, that every step ran in order, that each produced a schema-valid output, which edge was taken and why, which instructions were used, and that nobody edited the record afterwards.

How a run executes (MCP contract v2.1)

Four tools are exposed in every project: workflow.start, workflow.next, workflow.report and workflow.eval. This section describes server-orchestrated mode, the default; model-orchestrated mode is described below.

  1. workflow.start {request | input, evalCase?}: the server validates the flow and the run input (against the project's input schema, when it has one), freezes a snapshot of everything the run uses, and returns step 1: the agent's instructions and the JSON Schema its output must satisfy.
  2. workflow.next {runId, step, outputs: [{node, output}], transition?}: the client hands back one output per dispatched node. If any is missing or invalid, or the step number is not the current one, the call is rejected and nothing is consumed.
  3. The server decides the next step and returns it, until the run reaches an End node.

Retries are safe: resending the last accepted call returns the same answer without advancing. Every advance happens in a single database transaction together with its audit events.

Execution modes: server-orchestrated and model-orchestrated

Each project has a switch in Settings → Execution mode (also PATCH /projects/:id/execution-mode, or execution_mode in a harness). The mode is frozen in the run when workflow.start is called, so switching never affects runs in flight, and the client's tools and CLAUDE.md rule stay the same in both modes.

  • Server-orchestrated (default): everything on this page. The server hands out one step at a time and checks every output, transition and cap.
  • Model-orchestrated: workflow.start returns the whole flow in one document (every node's instructions and output shape, the routing with edge ids, rule edges written out for the model to evaluate, caps and outcomes). The model runs it on its own and finishes with workflow.report {runId, report}: its own account of the path, invocations and findings. The run goes from delivered to reported; it is never completed, because only the server can complete a run.

What model-orchestrated mode gives up: no output validation, no enforced transitions or caps, no way to stop a run midway (cancelling only refuses its report), no external MCP tools, and every agent's instructions are sent, including branches that are not taken. What it keeps: the same flow validation and frozen snapshot at start, the report stored whole with its SHA-256 and chained as a report.received event, and honest labels: model-orchestrated runs are "self-declared" in Audit and Analytics, never counted as verified, and their usage is capped at what the flow allows. Analytics replays a model-orchestrated run's reported path against its flow to flag agents the path required but the report skips. Eval runs always execute server-orchestrated, whatever the project's mode, and the review runners refuse model-orchestrated exports by default.

Dispatched is not completed

A step is dispatched when its instructions are sent, and completed only when its output is accepted. Eval grading and the audit trail count only completed steps. Usage analytics also shows model-orchestrated runs' self-declared usage, labelled as such. Outputs are stored whole, never truncated, with their SHA-256. When the run input lists changed_files, the server also rejects any finding whose file is not in that list.

Transitions the server decides or checks

  • One exit: taken.
  • Rule exits (when: {path, op, value} with eq, ne, in, gt, gte, lt, lte, exists and all/any): evaluated by the server, in priority order, on the validated output. The client does not choose.
  • Natural-language exits (condition): the client picks one by its exact edge id. Agent names, condition text and partial matches are refused.
  • A node with several exits has exactly one default edge. There is no "none": a run completes only at an End. Other endings are capped, cancelled and failed; a run idle for 2 h shows as abandoned and resumes if the client comes back.
  • Forks: a Parallel node fans out to agent branches that all join one node. The server waits for every branch output before moving on.

Flows are validated when saved and again at workflow.start: unique ids, known node types, every node reachable from Start and able to reach an End, exits for every non-End node, the fork shape, and an output schema wherever rule edges need one.

Instructions frozen per run

At workflow.start the server copies the flow, the project settings and every agent, skill and context the run uses into run_snapshots, each with its SHA-256. Steps are rendered from that copy, so editing an agent mid-run changes nothing for runs already in flight. Deleting an entity that a saved flow depends on is refused with 409.

Non-Markdown files attached to agents, skills or contexts (scripts, configs) are withheld from the prompt unless the project explicitly enables them.

What the server guarantees, and what it does not

In server-orchestrated mode, guaranteed: the order of steps; that every completed step produced an output of the declared shape; that transitions follow the graph (decided by the server for rule edges); that the run used the instructions it started with; that external tools were only called during the run, by an agent allowed to call them; and that the history cannot be changed without breaking the hash chain and the signature. Model-orchestrated runs only guarantee the flow validation, the frozen snapshot and that the stored report is the one chained.

Not guaranteed: that the model did the work well. A schema-valid output can still be wrong, and content in a diff can mislead the model. That is why the reference review harness has a verifier step, keeps its results advisory, and measures quality with evals built on pull requests with seeded bugs.

Audit chain and verification

A server-orchestrated run writes run.started, step.dispatched, step.completed, transition.taken, tool.called and a final run.completed, run.capped, run.cancelled or run.failed event. A model-orchestrated run writes run.started, then report.received (or run.cancelled). Each event hash covers the previous hash and the canonical JSON of the event; database triggers make the table append-only.

The export (aiorc.audit.v2) carries the event chain, the manifest of frozen entities and their hashes, every accepted output, the engine version, the run's execution mode (with the self-declared report of a model-orchestrated run, checked against its chained hash), the verified and the declared caller, and the commit the run input declares it reviewed (repo, base_sha, head_sha, pr_number, diff_sha256), as supplied by the caller. It is signed with Ed25519. Anyone with the public key can verify it offline with npm run audit:verify, or on the server with POST /audit/verify.

Harnesses and review runners

A harness is a directory: harness.json (projects, flows, evals), one folder per agent with AGENT.md and output.schema.json, plus skills and contexts. npm run harness:apply validates it with the server's own validators and loads it idempotently, so harness changes go through pull requests. The reference code-review harness reviews a change before a pull request (locally, with a script or a git hook) and after it (a GitHub Actions template that verifies the signed export before publishing an advisory check).

Limitations

1. One round trip per step

Each step costs a call to the server. The price buys the guarantees above; flows with many tiny steps feel it most. A project can switch to model-orchestrated mode to remove the round trips, at the cost of the execution guarantees.

2. Fork branches are a single agent

Each branch of a Parallel node is one agent whose only exit is the join. Multi-step branches are not supported yet.

3. Rules are edited as files

The editor preserves and shows rule edges, but writing rules and output schemas happens in the harness files or the API, not on the canvas.

4. Single node

SQLite and in-memory login throttling assume one server process.

Audit logging and the EU AI Act (Article 12)

Article 12 of the EU AI Act requires high-risk AI systems to support automatic event logging across their lifetime, with logs that allow tracing how each output was produced (retention of at least six months under Articles 19/26). AIOrc's audit layer supports that requirement for agentic workflows run in server-orchestrated mode:

  • Per-step events: every dispatch, completed output, transition (and what decided it) and tool call is an event in an append-only hash chain, with timestamps and the caller's identity (verified through a personal access token, or marked as declared).
  • Interpretability: the Audit page reconstructs any run step by step with its outputs; the same data is available as a signed JSON export.
  • Tamper evidence: exports are signed with Ed25519 and verifiable offline with the public key; editing any event breaks every hash after it.
  • Tool-call trail: calls to external MCP servers proxied through AIOrc are logged with server, tool, caller, outcome and latency.
  • Retention: runs and telemetry live in the instance database with no automatic expiry; the retention policy is in your hands (the deadline for high-risk obligations moved to December 2027 under the 2026 Digital Omnibus, but the logging architecture is in place today).

This does not make a deployment "compliant" by itself — compliance is a property of the whole system — but the event log Article 12 asks for is what server-orchestrated runs produce as a side effect.

Gating agent changes with evals

Evals turn "I think this change improved the agent" into a measurable verdict. The recommended working pattern:

  1. Define 3-10 eval cases per flow (in the harness files, or Usage analytics → Evals): a fixed input, the exact End it must reach, the agents that must complete a step, and for review flows the findings a seeded bug must produce ({file, category, min_severity}) with a cap on extra findings.
  2. Before changing an agent or the flow, run the suite from any MCP client: call workflow.eval, then workflow.start with each case id. Eval runs always execute server-orchestrated, and the server grades each run from its event chain; the model never grades its own work.
  3. Change the agent. Run the suite again.
  4. Compare pass rates in the Evals table. A drop means the change broke a path your team depends on — fix it before anyone else hits it.

Eval verdicts also appear per-run in the Audit page, so a failing case is traceable step by step.
