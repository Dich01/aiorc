Methodology

How the runs were set up and graded, and what they cannot tell you.

  1. Setup. Each case is one commit on a throwaway copy of a private production codebase, which is not named here; the original repository was only read, never changed. Two AIOrc projects with an identical review harness reviewed the same commits at the same time, one per mode: scope, six reviewers in parallel, verifier, PR proposal and release gate. Client: Claude Code in headless mode, default model, read-only tools, 3 cases in parallel per mode, 3 repetitions.
  2. Speed and cost are wall-clock seconds from start to signed export, and Claude Code's own total_cost_usd and token counts. Both modes ran concurrently on the same machine.
  3. Suites. Base: 13 cases, a single-file defect each (10) or a clean change (3). Complex: 20 cases (15 defect, 5 clean) with two defects in one change, defects that only show across files, subtle domain and logic errors (limits, signed authorizations, time windows) and defects buried in large refactors; its clean changes correctly touch security-sensitive code.
  4. Grading. Every signed export is verified first. A server-orchestrated run is graded from its last validated step; a model-orchestrated run from its self-declared report, whose hash is checked against the chain but never against what actually ran. A defect counts as found when a final finding matches its file, category and minimum severity; a run passes when it reaches an End, every seeded defect is found and extra findings stay within 3 (defect) or 1 (clean).
  5. Blocked means the release gate ended the run at changes-requested. Within schema counts final findings that carry every required field of the harness finding schema; the server rejects the others in server-orchestrated mode.
  6. The one miss (case C09, one model-orchestrated repetition) is a grading artefact: the model reported the secret moving into the query string, at high severity in the right file, but filed it under secrets instead of security.
  7. What the numbers cannot show. Detection was equal, but in a model-orchestrated run nothing on the record proves the reviewers ran: the report says they did. Server-orchestrated runs carry a validated, hash-chained output for every step.
  8. Limits. Three repetitions per case and mode; model output is not deterministic, so differences of a few seconds or one finding are within noise. The defects were written for the benchmark, and the complex answer key was reviewed for being defensible, not by the codebase's maintainers.
  9. Data. The anonymised results behind this page, one row per graded run: code-review-2026-11-09.json. The codebase, its file paths and the exact seeded changes are not published.
