AIOrc: compilador de workflows multi-agente sobre MCP

AIOrc compila grafos de workflow visuales en un único prompt determinista que el modelo destino ejecuta secuencialmente vía Model Context Protocol. A diferencia de orquestadores con runtime activo (LangGraph, CrewAI, AutoGen, Claude Agent SDK), AIOrc emite el flujo completo en una sola llamada MCP — eliminando la latencia inter-agente y manteniendo la coherencia de contexto en una sola sesión LLM.

Resumen y posicionamiento

Los frameworks de orquestación multi-agente (LangGraph, CrewAI, AutoGen, Semantic Kernel) abordan el problema "cómo coordinar varios LLMs en una tarea" desde el lado del runtime: mantienen un loop de control activo, llaman al LLM por cada agente, persisten estado compartido, y deciden el próximo paso después de cada respuesta. Es flexible, pero tiene tres costos: latencia acumulada por cada round-trip, fragmentación del contexto entre agentes, y un runtime de orquestación que vive en el destino.

AIOrc plantea una alternativa: si el grafo del flujo es conocido a priori — con sus bifurcaciones, ciclos y forks paralelos — entonces se puede compilar antes de ejecutar. El producto de la compilación es un único documento markdown que describe agentes, skills, topología y reglas de recorrido. El LLM destino lo carga una vez y recorre el grafo en su propio razonamiento, en una sola sesión. No hay runtime activo. No hay round-trips. No hay estado compartido fuera del propio contexto del LLM.

Hallazgo clave

Un flujo de 5 agentes que en un orquestador tradicional implica 5 llamadas LLM secuenciales (con sus respectivas latencias de red, validación de schema, y serialización), en AIOrc implica una sola llamada MCP que retorna el workflow compilado — y el modelo destino recorre la topología dentro de su propia sesión, donde la "latencia" inter-paso es velocidad de generación de tokens. Cuando hay nodos parallel, el LLM puede además disparar varias ramas en una misma respuesta vía Agent tool calls concurrentes.

El trade-off es conocido y explícito: AIOrc no soporta intervención mid-run, no permite streaming intermedio entre agentes, y depende del LLM destino para interpretar las condiciones en lenguaje natural y respetar los caps por agente. A esto lo llamamos determinismo blando — el flujo es determinista en estructura (siempre el mismo prompt para el mismo grafo + input) pero su recorrido depende de la fidelidad del LLM al prompt.

  • src/routes/flows.ts — PUT/GET de flujos por proyecto, con whitelist y persistencia en project_flows.flow_json.
  • src/routes/{projects,agents,skills,users,issues,invitations,runs,auth}.ts — CRUD multi-tenant: fork, stars, visibilidad pública, invitaciones, módulo de issues comunitario.

Sin Redis, sin colas, sin workers, sin contenedores. Single binary node + single SQLite file + un bundle Vite estático para el flow editor. El argumento es: si el flujo se compila en pocos milisegundos y la ejecución la hace el LLM destino, no necesitamos infrastructure de orquestación.

Por qué compilar en lugar de orquestar

Latencia inter-agente

En un orquestador tradicional, la latencia total de un flujo de N agentes es aproximadamente:

latencia_total ≈ Σᵢ (red_call_i + tokens_in_i / throughput + serialización_i + decisión_i)

Donde cada término del sumando incluye el round-trip de red al proveedor LLM, la generación de tokens, y la decisión del orquestador sobre qué hacer después. Para 5 agentes con respuestas medianas, esto suele ser 8-30 segundos solo en orquestación.

En AIOrc, la latencia es:

latencia_total ≈ red_compilación + tokens_in_total / throughput

Una sola llamada MCP local (~1-5ms) y la generación tokenizada del flujo entero. Sin pausas entre pasos.

Coherencia de contexto

Los frameworks multi-agente típicamente aíslan el contexto de cada agente, pasando solo subsets relevantes via tool calls o shared state. Esto es deliberado — busca evitar context bloat y delegar limpiamente — pero introduce un costo: el modelo nunca tiene visión total. Un agente downstream no sabe qué razonó el upstream, solo el output literal.

AIOrc inyecta el flujo entero como un único documento markdown en el contexto del modelo destino. Cada paso ve los pasos previos y los pasos siguientes. Esto permite consistencia interna, referencias cruzadas ("como dijo task-planner"), y razonamiento transversal sobre el flujo completo.

Sin runtime de agentes en el destino

El proyecto destino no necesita instalar LangChain, CrewAI ni ningún SDK de orquestación. Solo necesita:

  1. Un cliente MCP — Claude Code, Cursor, Continue, o cualquier IDE compatible con MCP ya tiene esto.
  2. El bridge stdio de AIOrc (mcp-bridge.js, ~50 líneas).
  3. Una regla en CLAUDE.md que indique al modelo llamar a workflow() antes de responder.

Esto reduce el blast radius: el destino sigue siendo un proyecto de código común, no un proyecto con runtime de orquestación entrelazado.

Cómo funciona el compilador

El núcleo del sistema es compileFlow(projectId, input) en src/orchestrator/index.ts. A diferencia de orquestadores con runtime activo, AIOrc no ejecuta el flujo — lo transcribe a un documento markdown que describe topología, agentes y reglas para que el LLM destino lo ejecute en su propio razonamiento. El grafo tiene cuatro tipos de nodo y aristas con condiciones en lenguaje natural:

// src/db/schema.ts export type FlowNodeType = 'start' | 'agent' | 'parallel' | 'end'; interface FlowNode { id: string; type: FlowNodeType; agent_id?: string; // solo para type='agent' agent_name?: string; // denormalizado para display max_invocations?: number; // solo para 'agent', default 10, cap 50 outcome?: string; // solo para 'end', etiqueta libre label?: string; // usado típicamente por 'parallel' x: number; y: number; } interface FlowEdge { id: string; from: string; to: string; condition?: string; // lenguaje natural; absent = fallback priority?: number; // menor evalúa primero; default 1000 }

No hay primitivas separadas para "decisión", "gate" o "loop". Esa expresividad emerge de la combinación de aristas con condiciones, prioridades y back-edges:

  • Bifurcación: varias aristas saliendo de un mismo agente, cada una con su condition en lenguaje natural. El LLM evalúa el output del agente y elige una sola transición.
  • Gate: un agente que emite un verdict en su output (PASS/FAIL/score≥X/etc.) seguido de aristas con condiciones que matchean ese verdict. La estructura es la misma que una bifurcación.
  • Loop: una arista que apunta hacia atrás (back-edge). Los ciclos están permitidos por construcción; el cap es per-agent (max_invocations, default 10, máximo 50) y lo enforca el LLM contando sus propias invocaciones.
  • Fork/Join: el nodo parallel. Tiene ≥1 incoming y ≥2 outgoing edges, todas tomadas concurrentemente. El LLM dispara las ramas en paralelo (idealmente una Agent tool call por rama en una misma respuesta) y espera a que todas terminen.

Algoritmo de compilación

  1. Carga del flujo. Lee project_flows.flow_json y los agentes referenciados. Si no hay flow o está vacío, retorna error no_flow/empty_flow.
  2. Normalización (normalizeFlow). Aplica defaults: priority=1000, max_invocations clampeado a [1, 50], condition normalizado a string non-empty o undefined.
  3. Validación fail-closed (validateFlow). Cinco reglas estructurales: exactamente 1 Start (con 0 incoming, 1 outgoing), Ends sin outgoing, Agents con agent_id que existe en el proyecto, aristas con extremos válidos, Parallels con ≥1 incoming y ≥2 outgoing. Si hay errores, se retorna invalid_flow con los mensajes concatenados — el cliente MCP los recibe en el JSON-RPC error.
  4. Hoist de skills. Recolecta las skills únicas referenciadas por todos los agentes y las emite una sola vez arriba del prompt. Cada agente las referencia por nombre, evitando duplicación de tokens.
  5. Emisión de sub-agentes. Para cada nodo agente, emite un bloque con nombre, max_invocations, descripción, expected_output_format, skills aplicadas (referencia a la sección hoisted) y contenido del agente.
  6. Emisión de topología. BFS desde Start construyendo la lista ordenada de nodos. Para cada nodo no-end emite sus aristas salientes ordenadas por priority ascendente, mostrando label de destino y condición (o "sin condición — fallback").
  7. Reglas de ejecución. Once reglas literales que le explican al LLM cómo recorrer el grafo: cómo elegir transición, qué hacer en parallel, cuándo terminar, cómo contar invocaciones por agente, qué hacer ante ambigüedad.
  8. Persistencia del run. Inserta una fila en runs con el workflow_snapshot completo. Esto da auditoría reproducible: el mismo flujo + mismo input genera el mismo prompt.

Ciclos como back-edges, no como primitiva

Los ciclos están permitidos por construcción — no hay una validación que los rechace y no hay is_loop_back en el modelo. El compilador no expande ni desenrolla nada: si la topología tiene un ciclo code-reviewer → bug-resolver → code-reviewer, eso se emite como dos aristas y listo. El LLM destino las ve, evalúa las condiciones cada iteración, y mantiene el conteo por agente.

El cap viene del agente, no del loop: cada FlowNode de tipo agent tiene un max_invocations (default 10, clampeado a 50). Cuando el LLM llega al máximo y la topología querría volver a invocarlo, la regla 7 del prompt le instruye cortar el flujo y reportar al usuario. Es soft-determinism: el enforcement vive en el prompt y depende de que el modelo cuente honestamente sus invocaciones.

Convergencia: emergente, no detectada

Cuando dos ramas de un fork (o una bifurcación condicional) vuelven a un nodo común, el compilador no calcula puntos de convergencia ni emite el subgrafo común "una sola vez". Simplemente lista cada arista en la sección de topología. El LLM ve que dos transiciones llegan al mismo nodo y lo invoca una vez después de consolidar las ramas. Esto evita un análisis costoso de reachable sets a cambio de delegar la coordinación al modelo destino, que ya tiene el grafo entero en su contexto.

Estructura del mega-prompt

El output del compilador es un documento markdown con cinco secciones, ordenadas para que el LLM destino tenga toda la información antes de empezar a recorrer la topología. No usamos numeración de "STEPs" ni verdicts literales — el LLM es el que decide qué transición tomar según las condiciones en lenguaje natural de cada arista. Este es el esqueleto real generado por src/orchestrator/index.ts:

# AIOrc — Workflow Multi-Agente Sos el orquestador. Tenés disponibles los siguientes sub-agentes y una topología recomendada para invocarlos. Seguí la topología como guía; las condiciones en las aristas son hints en lenguaje natural — interpretalas con criterio. ## Input del usuario (si vino algún payload en la llamada MCP) ```json { "request": "...", "context": "..." } ``` ## Skills (reglas obligatorias) // Hoisted: cada skill referenciada por algún agente, una sola vez. ### Skill: tdd-governance *description...* [contenido completo de la skill] ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━ ## Sub-agentes disponibles ### Agente: task-planner **Máximo de invocaciones:** 10 **Descripción:** Analiza el requerimiento del usuario... **Formato de output esperado:** JSON con field 'intent' **Skills aplicadas:** (referencias por nombre a la sección "Skills" de arriba) - *tdd-governance*: ... **Instrucciones del agente:** [contenido del agente] **Verificación obligatoria:** releé tu output y confirmá que cumple cada skill aplicada antes de pasar al siguiente paso. ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━ ## Topología del flujo **Punto de entrada (Start):** comenzá invocando al sub-agente *task-planner*. **Aristas (transiciones permitidas):** - Desde *task-planner*: → *bug-resolver* *cuando:* el output indica que es un bug → *new-feature* *cuando:* el output indica que es una feature - Desde *bug-resolver*: → *code-reviewer* *(sin condición — fallback)* - Desde *code-reviewer*: → *bug-resolver* *cuando:* verdict == FAIL y queremos otra iteración → 🏁 End: "merged" *cuando:* verdict == PASS ## Reglas de ejecución 1. Empezá por el punto de entrada (Start)... 2. Después de cada agente, evaluá las condiciones de sus aristas salientes y elegí UNA sola transición. 3. Las condiciones son lenguaje natural — interpretalas según el output del agente anterior. 4. Si una arista no tiene condición, es el fallback default. 5. Si TODAS tienen condición y NINGUNA coincide, terminá exitosamente. 6. Las aristas hacia un agente anterior son legítimas — implementan loops/reintentos. 7. **Cap por agente:** llevá la cuenta. Si llegás al máximo y la topología te quiere mandar de nuevo a él, cortá y reportá al usuario. 8. **Nodos Parallel (⫲):** disparás TODAS las ramas concurrentemente (idealmente una Agent tool call por rama en una misma respuesta). Esperá a que todas terminen y consolidá antes de avanzar. 9. Si llegás a un nodo End, terminá y reportá su outcome. 10. Si llegás a un agente sin aristas salientes, terminá. 11. Si no podés decidir entre varias transiciones, parar y consultar al usuario. ## Outcomes posibles del workflow - merged - abandoned ## Reporte opcional Cuando termines, OPCIONALMENTE llamá `workflow.report` con: ```json { "runId": "...", "report": { "path": [...], "invocations_per_agent": {...}, "ended_at": "...", "final_summary": "..." } } ```

Hay decisiones de diseño deliberadas detrás de cada elemento:

  • Skills hoisted: las skills se emiten una sola vez al inicio, y cada agente las referencia por nombre. Una skill compartida por 5 agentes consume tokens ×1, no ×5.
  • Condiciones en lenguaje natural: en lugar de exigir verdicts literales (PASS/FAIL/BLOCKED) como machine-readable, las condiciones son texto libre que el LLM evalúa contra el output del agente. Es menos rígido pero más expresivo y reduce el costo de diseño del flow.
  • Topología como lista de aristas, no como árbol numerado: el LLM ve el grafo entero, no una secuencia pre-linealizada. Esto permite ciclos sin necesidad de primitivas LOOP, y bifurcaciones sin necesidad de primitivas DECISION.
  • Cap por agente, no por loop: max_invocations es per-agent y se enforca en la regla 7. El LLM lleva el conteo explícito en su propio razonamiento.
  • Fallback explícito: una arista sin condición es la transición por defecto cuando ninguna otra matchea. Si todas tienen condición y ninguna matchea, el workflow termina exitosamente (regla 5).
  • Verificación post-output: cada bloque de agente con skills incluye una "verificación obligatoria" que le pide al LLM releer su output y validarlo contra las skills antes de continuar.

Determinismo blando: por qué funciona

AIOrc no tiene un mecanismo de enforcement programático — no hay un agente coordinador que valide cada paso del modelo destino. La fidelidad del flujo depende enteramente de que el LLM respete las instrucciones del prompt compilado. A esto lo llamamos determinismo blando.

Esto suena frágil, pero en la práctica funciona bien por varias razones:

  • Los LLMs siguen instrucciones bien estructuradas mejor que código frágil. Un orquestador con código que valida outputs y reintenta es más predecible en teoría, pero en la práctica frecuentemente falla por edge cases del schema. Un prompt imperativo claro no tiene esos edge cases.
  • El modelo destino mantiene el contexto entero. Mientras ejecuta el paso 4, sigue viendo los pasos 1-3 y sabe qué viene en 5-7. Esto le da consistencia interna que un orquestador con contexto fragmentado no tiene.
  • Patrones empíricamente robustos. "elegí UNA sola transición", "llevá la cuenta de cuántas veces invocaste cada agente", "esperá a que TODAS las ramas terminen", "si no podés decidir, parar y consultar al usuario" — instrucciones declarativas que los LLMs modernos respetan con alta fidelidad cuando están en el contexto activo.
Validación empírica

En tests del usuario sobre flujos con bifurcaciones (varias aristas con condiciones desde un mismo agente) y ciclos (back-edges con cap por max_invocations), Claude Sonnet 4.5+ interpretó correctamente las condiciones en lenguaje natural y respetó los caps en los casos probados, incluyendo escenarios donde el prompt era ambiguo y requería decidir intent sin pistas explícitas.

Donde el determinismo blando puede fallar (y cómo mitigarlo):

  • Modelo más viejo o más débil interpreta mal una condición en lenguaje natural — Mitigación: probar el flujo con el modelo destino antes de productizarlo. Si Sonnet 4.5 lo respeta y Sonnet 3.5 no, exigir versión mínima.
  • El modelo toma dos ramas a la vez en lugar de elegir una — Mitigación: la regla 2 del prompt ("elegí UNA sola transición") más prioridades distintas (priority en cada arista) hacen que la primera condición que matchea gane.
  • El modelo excede el cap de un agente — Mitigación: la regla 7 instruye explícitamente cortar + reportar al usuario. En tests reales, los modelos modernos cuentan honestamente sus invocaciones porque deben escribirlas en el output.
  • El modelo malinterpreta un parallel y serializa — Mitigación: la regla 8 le explica que debe disparar todas las ramas en una misma respuesta (vía Agent tool calls paralelas). Si no es viable técnicamente, las ejecuta secuencialmente sin elegir.

Comparativa con frameworks 2026

El espacio de orquestación multi-agente cambió mucho entre 2024 y 2026. Aparecieron Claude Agent SDK (Anthropic, fines 2025) y OpenAI Agents SDK (2025) como ofertas oficiales de los proveedores de modelos. LangGraph maduró hacia stateful workflows, CrewAI se enfocó en colaboración rol-based, y AutoGen (ahora bajo el AG2 fork comunitario más Microsoft Agent Framework oficial) se mantiene en el nicho conversacional.

AIOrc no compite directamente con ninguno — ocupa el nicho compile-time, single-call, MCP-native que ningún framework grande cubre actualmente:

"AIOrc trabaja bien donde el grafo es estable. Si tu workflow se ramifica dinámicamente según outputs intermedios que no podés predecir, necesitás un orquestador con runtime (LangGraph, Claude Agent SDK). Diferencias clave por framework

vs. Claude Agent SDK: Claude Agent SDK es la oferta oficial de Anthropic para construir agentes basados en Claude (lo que el equipo de Claude Code usa internamente). Ofrece subagents, tools customizables, hooks programáticos y context management. Es runtime-based y vive en el código del proyecto. AIOrc, en cambio, define el flujo afuera del proyecto destino — el destino solo necesita MCP. Si tenés autoridad sobre el código del destino y querés control fino programático, Claude Agent SDK es más poderoso. Si querés definir flujos centralizadamente y reutilizarlos en N proyectos sin tocarlos, AIOrc es más práctico.

vs. LangGraph: LangGraph asume que vas a escribir Python para definir el grafo, y que querés state management con checkpoints, time travel, y human-in-the-loop. AIOrc descarta todo eso a cambio de un grafo visual, persistido como JSON, ejecutable en un solo round-trip.

vs. OpenAI Agents SDK: Más simple que LangGraph, basado en handoffs entre agents. Solo OpenAI. AIOrc es model-agnostic en principio (cualquier MCP client) pero está optimizado para Claude.

vs. CrewAI: CrewAI brilla cuando los agentes deben colaborar de forma rol-based (researcher → writer → editor) con manager opcional. AIOrc no piensa en términos de roles sino de pasos de un grafo.

Caso de estudio: bug vs feature con QA paralelo

Un flujo realista que ejercita los cuatro tipos de nodo: start, varios agent, un parallel de QA, un ciclo de review→fix, y dos end con outcomes distintos. Toda la lógica condicional vive en las aristas, no en primitivas separadas:

🟢 Start │ ▼ [task-planner] (max_invocations: 5) │ ├──► cuando: el output indica que es un bug │ [bug-resolver] (max_invocations: 8) │ │ │ └────┐ │ ▼ ├──► cuando: el output indica que es una feature │ [new-feature] (max_invocations: 8) │ │ │ └────┐ │ ▼ │ [backend-dev] (max_invocations: 10) │ │ │ ▼ │ ⫲ Parallel: QA gates │ ├──► [code-reviewer] │ └──► [security-qa] │ │ │ ▼ │ ┌─ cuando: ambos verdicts indican PASS │ │ 🏁 End: "merged" │ │ │ └─ cuando: alguno indica FAIL │ ▼ │ (back-edge) → [backend-dev] // cycle, capped por max_invocations

Flujo bug-vs-feature: bifurcación por condición en aristas, fork paralelo de QA, ciclo de fix vía back-edge, dos outcomes terminales.

Cómo se traduce a primitivas reales

  • Bifurcación bug vs feature: dos aristas saliendo de task-planner, cada una con su condition en lenguaje natural. No hay nodo "decision" — el LLM evalúa el output del planner y elige una.
  • QA paralelo: un nodo parallel con dos aristas salientes a code-reviewer y security-qa. La regla 8 le instruye al LLM disparar ambas en una misma respuesta (vía Agent tool calls concurrentes) y esperar el join.
  • Ciclo de fix: una arista QA → backend-dev que apunta hacia atrás. El LLM la sigue cuando la condición matchea, y respeta max_invocations sobre backend-dev contando sus propias llamadas.
  • Outcomes: dos nodos End con outcome distinto ("merged", "abandoned"). El LLM reporta el outcome alcanzado al terminar.

Resultados empíricos

Probado con prompts ambiguos donde el intent no se declara explícitamente:

  • "el endpoint /api/users devuelve 500 cuando el body está vacío" → planner clasifica como bug → arista a bug-resolver. ✓
  • "agregar paginación a /api/products" → feature → new-feature. ✓
  • "crea un endpoint que devuelva hola mundo" → feature → new-feature. ✓

El ciclo review-fix-review se ejecutó 1-3 veces dependiendo del verdict del code-reviewer, sin exceder el cap (max_invocations: 10 en backend-dev) en ninguno de los tests. El parallel disparó ambos QA agents concurrentemente en la respuesta del LLM, y el join consolidó los verdicts antes de avanzar.

Limitaciones técnicas

1. Context size escala linealmente con el flujo

Cada agente embebe su contenido completo en el prompt compilado. Un flujo de 12 agentes con 2KB de contenido cada uno produce un prompt de ~24KB sólo de instrucciones (sin contar el request del usuario ni el output que el modelo va generando). Para Claude Sonnet con context de 200K, esto sigue siendo marginal — pero flujos de 30+ agentes con prompts extensos pueden acercarse al límite efectivo (donde la performance del modelo decae por context rot).

Mitigación: escribir agentes concisos, apoyarse en skills externas (que se referencian por nombre en lugar de embeberse), y dividir flujos grandes en sub-flujos jerárquicos. La división jerárquica no está implementada aún en AIOrc.

2. No hay streaming intermedio

El usuario final no ve resultados parciales hasta que el flujo termina. Si un agente intermedio falla, el output completo se pierde. Para tareas largas (más de 60 segundos de generación) esto es notable.

Mitigación: diseñar flujos cortos donde el costo de re-run es bajo, y confiar en workflow.report opcional para auditoría post-hoc.

3. No hay interrupción mid-run

Una vez que el modelo empieza a ejecutar el flujo compilado, no se puede inyectar feedback. Si el usuario detecta un error temprano, debe esperar al final.

4. Paralelismo delegado al LLM

El nodo parallel existe en el modelo y el compilador lo emite con la instrucción de dispararse vía Agent tool calls concurrentes, pero el paralelismo real depende de que el cliente MCP soporte tool calls múltiples por respuesta. Si el cliente no lo hace, el LLM serializa las ramas — sigue siendo correcto, pero pierde la ganancia de wall-clock. LangGraph y CrewAI manejan el paralelismo en código del orquestador, no en el cliente.

5. El cap por agente depende del LLM

El max_invocations de cada agente lo enforca el prompt (regla 7) y depende de que el LLM cuente honestamente sus propias invocaciones. En la práctica, los LLMs modernos respetan el cap con alta fidelidad porque deben escribir el conteo en su propio output, pero no hay enforcement programático: si el modelo "miente" sobre cuántas veces invocó algo, no hay un orquestador externo que lo corte.

Soft determinism

Los puntos 1-5 son consecuencias del approach compile-time. Son trade-offs deliberados, no bugs. Si necesitás cualquiera de esas capacidades como requisito duro, un orquestador con runtime es la elección correcta.

Cuándo usar AIOrc (y cuándo no)

Usá AIOrc cuando

  • Tenés flujos bounded y predecibles — 3 a 12 agentes, con bifurcaciones, ciclos y forks paralelos conocidos a priori.
  • Querés latencia mínima por run — single MCP call beats N runtime calls.
  • El destino ya es Claude (Claude Code, Cursor, o cliente MCP-compatible).
  • Necesitás auditoría reproducible — workflow_snapshot + execution_report dan trazabilidad completa.
  • Querés evitar instalar runtime de orquestación en el proyecto destino.

Casos de uso ideales: code review pipelines, on-call playbooks, ETL determinístico, QA gates con criterios fijos, generación de documentación a partir de specs, refactor pipelines.

NO uses AIOrc cuando

  • Necesitás conversación multi-turn con el usuario en medio del flujo.
  • Necesitás streaming intermedio con UI mostrando progreso paso a paso.
  • Tenés agentes que llaman herramientas externas en paralelo y los resultados deben unirse dinámicamente.
  • El flujo es exploratorio y se ramifica dinámicamente según resultados que no podés modelar a priori.
  • Necesitás human-in-the-loop con interrupciones reales.

Para esos casos: LangGraph (state-based con interrupts), CrewAI (rol-based), AutoGen (conversacional).

[2] Anthropic — Claude Agent SDK
Oferta oficial de Anthropic para construir agentes Claude programáticos (subagents, hooks, context management). El "competidor" runtime más directo cuando se quiere control fino sobre cada paso del agente. docs.anthropic.com/agent-sdk
[3] OpenAI — Agents SDK
SDK lanzado por OpenAI en 2025 para orquestación multi-agente con handoffs y guardrails. Específico al ecosistema OpenAI. openai.github.io/openai-agents-python
[4] LangGraph — stateful multi-agent orchestration
Loop de orquestación con shared state, checkpoints, streaming y human-in-the-loop. El competidor más maduro cuando se necesita runtime activo y persistencia de estado. langchain-ai.github.io/langgraph
[5] CrewAI — role-based multi-agent collaboration
Framework para agentes con roles asignados colaborando en una meta compartida. Comunicación inter-agente vía crew memory. crewai.com
[6] Microsoft Agent Framework / AutoGen
Agentes conversacionales que dialogan entre sí. La línea AutoGen original se reorganizó en 2025: el fork comunitario AG2 mantiene el legado, y Microsoft lanzó Agent Framework como su oferta oficial (unificando AutoGen + Semantic Kernel). github.com/microsoft/agent-framework
[7] Pydantic AI — typed agents
Framework Python que expone agentes con validación Pydantic, focalizado en type-safety y composición. Alternativa lightweight a LangGraph para casos simples. ai.pydantic.dev
[8] Anthropic Claude Code — IDE agentic con MCP nativo
Cliente MCP de referencia con el que se probó AIOrc. La integración se hace vía .mcp.json en el directorio del proyecto. AIOrc fue diseñado para integrar con clientes MCP como este. claude.ai/code
[9] arXiv 2604.05150 — Static Analysis of LLM-Orchestrated Programs (Apr 2026)
Investigación reciente sobre análisis estático de workflows AI compilados en build time. Comparte la filosofía compile-time desde un ángulo distinto (verificación formal de propiedades del flujo). arxiv.org/abs/2604.05150
[10] Liu et al. — Lost in the Middle: How Language Models Use Long Contexts (2023)
Trabajo seminal sobre context rot. Relevante para AIOrc porque embebe el flujo entero en el contexto del modelo destino: justifica empíricamente por qué los flujos cortos (3-12 agentes) performan mejor que flujos masivos. arxiv.org/abs/2307.03172

El paper que estableció el patrón Thought→Action→Observation que la mayoría de frameworks multi-agente implementan. AIOrc lo evita: en lugar de loops Thought-Action en runtime, compila la estructura de razonamiento upfront. arxiv.org/abs/2210.03629
