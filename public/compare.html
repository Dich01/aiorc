How it compares · November 2026

A review bot reads the pull request. A harness on AIOrc gets the change ready before it exists.

AIOrc is the platform: it stores a company's agents, skills and contexts, runs their workflows one step at a time from the server, and signs a record of every run. What a workflow does is up to the harness you build on it. Ours is ready-for-pr: before a pull request is opened it runs the repository's own checks, several reviewers, a verifier that tries to prove each finding wrong, a capped fix loop, and writes the pull request with its evidence. We tested it with AIOrc on two production Python repositories, a payments library and the web platform that uses it.

What the platform gives every harness

Each one exists somewhere on its own. We did not find the three together in another product. Any harness on AIOrc gets them, not only ready-for-pr.

The server keeps the order

The model gets one step at a time. A step only counts when its output matches the agent's schema, and the server, not the model, decides where the run goes next. Skipping a reviewer is refused while it is being attempted, not discovered in a log afterwards.

Evidence you can verify offline

Every run is an append-only, hash-chained event log, exported and signed with Ed25519. An auditor needs the export and a public key, nothing else. Change one output and the chain breaks.

One shared library

Agents, skills and contexts live in a registry the whole company shares, forks and versions. A context goes only to the agent that needs it, so a security reviewer reads your infrastructure notes and nobody else pays for them. A fork is told when the original improves and updates in one step, keeping its own contexts.

Where it fits, and where it does not yet

AIOrc is not trying to replace the bot on your pull requests. A harness like ready-for-pr makes sure what reaches the pull request is already checked, reviewed and explained; the platform makes it the same for every team.

Good fit

  • Teams where agents write a lot of the code and reviewers cannot keep up.
  • Regulated or audited work, where "the AI reviewed it" needs a record someone else can check.
  • Several teams, one process. The flow is defined once and forked per repository, with each team's own checks and documents.
  • Mixed tools. Claude Code today, another MCP client tomorrow, same flow.

Where we are behind

  • No independent measure of detection quality yet. Every benchmark in this market is run by a vendor and they disagree with each other.2 Ours is too: we publish it on the benchmarks page with that caveat.
  • In ready-for-pr, the model runs the checks. AIOrc checks the shape of each result and the hash of the script that produced it, not that it really ran. The official result is still your CI.
  • A clean review can still fix the wrong cause. In one of our test runs every reviewer passed a fix for the cause the task named, while a likelier cause stayed untouched. The harness now treats the task's diagnosis as a hypothesis and asks for the original failure to be reproduced with the repository's real configuration; we have not measured yet how often that catches it.
  • Early. One maintainer, SQLite, single node.
