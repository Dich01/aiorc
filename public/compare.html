How it compares · November 2026

A review bot reads the pull request. AIOrc runs the whole process before it exists.

Most AI review tools show up once the PR is open and leave comments. AIOrc runs on the developer's machine first: the repository's own checks, several reviewers, a verifier that tries to prove each finding wrong, a capped fix loop, and a pull request that arrives with its evidence. The server holds the order of the steps, and every run can be exported as a signed record anyone can check.

Three things we did not find together anywhere else

Each one exists somewhere on its own. The point of AIOrc is having all three in the same place, for every team in the company.

The server keeps the order

The model gets one step at a time. A step only counts when its output matches the agent's schema, and the server, not the model, decides where the run goes next. Skipping a reviewer is refused while it is being attempted, not discovered in a log afterwards.

Evidence you can verify offline

Every run is an append-only, hash-chained event log, exported and signed with Ed25519. An auditor needs the export and a public key, nothing else. Change one output and the chain breaks.

One shared library

Agents, skills and contexts live in a registry the whole company shares, forks and versions. A context goes only to the agent that needs it, so a security reviewer reads your infrastructure notes and nobody else pays for them.

Where it fits, and where it does not yet

AIOrc is not trying to replace the bot on your pull requests. It makes sure what reaches the pull request is already checked, reviewed and explained.

Good fit

  • Teams where agents write a lot of the code and reviewers cannot keep up.
  • Regulated or audited work, where "the AI reviewed it" needs a record someone else can check.
  • Several teams, one process. The flow is defined once and forked per repository, with each team's own checks and documents.
  • Mixed tools. Claude Code today, another MCP client tomorrow, same flow.

Where we are behind

  • No independent measure of detection quality yet. Every benchmark in this market is run by a vendor and they disagree with each other.2 Ours is too: we publish it on the benchmarks page with that caveat.
  • The model runs the checks. The server checks the shape of each result and the hash of the script that produced it, not that it really ran. The official result is still your CI.
  • A review checks the change against the task. If the task's diagnosis is wrong, a clean review can still ship the wrong fix. We saw it in a real run and are adding a step that questions the diagnosis.
  • Early. One maintainer, SQLite, single node.
